# ADR 0008: PyMC + ArviZ for the bounded one-chain Bayesian pack

- Status: Accepted
- Date: 2026-07-28
- Work package: WP-H71a (PyMC + ArviZ bounded P1 candidate)
- Decider: SRL maintainers
- Supersedes: none
- Superseded by: none

## Context

WP-H71a introduces the first **actual-compute adapter** for a P1 candidate: the
`pymc_arviz` first-wave candidate card (`srl.packs.p1.FIRST_WAVE_CANDIDATES[0]`)
declares the PyMC probabilistic-programming capability surfaced through ArviZ
exploratory analysis and diagnostics. The candidate card carries the upstream
SPDX (Apache-2.0 for both) and a removal/rollback path, but no built adapter and
no resource measurement — so its P1 verdict is a typed `WAIT_*`. This ADR records
the decision to build the adapter, the one-chain bounded profile that bounds its
compute, and the removal strategy.

The adapter (`src/srl/packs/adapters/pymc_adapter.py`) must:

1. Fit a Bayesian posterior over a **restricted declarative model spec** (a
   normal-mean model and a linear regression) — no arbitrary code.
2. Run **exactly one chain**, always, refusing multi-chain requests with a typed
   `CONTRACT_INVALID`.
3. Require an explicit seed and bound draws/tune/wall time so the profile stays
   within the CI budget.
4. Return summary statistics as SRL decimal-string policy values, diagnostics
   (`rhat_max`, `ess_min`, `divergences`), a posterior predictive check, a
   resource measurement, and a `selection_note`.
5. Carry the selection-aware interpretation honestly: a fitted posterior is not
   model validation, not causal identification, and — for one chain — not a
   convergence certificate.

The adapter is a pack-scoped dependency behind
`srl.packs.adapters.pymc_adapter`; no other module in the SRL tree imports
`pymc`, `arviz`, or `pytensor`. The relevant capability profile is `uncertainty`
(the statistical profile in `src/srl/planning/profiles.py`).

## Alternatives considered

### 1. `pymc` + `arviz` (chosen)

- PyMC is the reference probabilistic-programming library for Python, maintained
  at `pymc-devs/pymc`. ArviZ is the reference exploratory-analysis and
  diagnostics library, maintained at `arviz-devs/arviz`.
- PyMC's `pm.sample` (NUTS) and ArviZ's `az.summary` / `az.ess` / `az.rhat` are
  exactly the operations a bounded one-chain profile needs, and they expose the
  diagnostics (`divergences`, `ess`, `r_hat`) the adapter surfaces.
- Both are **Apache-2.0**, compatible with the project's Apache-2.0 license and
  the SRL pack allowlist.

### 2. `numpyro` / `jax`-based samplers

- Excellent performance and a functional API, but pull the JAX/`jaxlib` native
  closure (large, platform-sensitive), and the diagnostics surface is split
  across libraries (ArviZ is still needed for summary/ess/rhat).
- Larger supply-chain surface than the WP-H71a *candidate* pack warrants.

### 3. Hand-rolled Metropolis / conjugate updates

- Avoid a runtime sampler dependency entirely for the normal-mean case (the
  conjugate posterior is analytic — see the conformance fixtures).
- But: the pack's job is to demonstrate the capability is wrappable with a real
  sampler; a hand-rolled conjugate updater would not exercise NUTS divergences
  (the H71a-03 diagnostics-flag check) and would not generalize to linear
  regression. The adapter intentionally uses a real NUTS sampler so the
  diagnostics surface is genuine.

## Decision

Adopt **`pymc>=5.20,<6`** and **`arviz>=0.20,<1`** as the Bayesian engine for
WP-H71a, **fully isolated behind the adapter**
`src/srl/packs/adapters/pymc_adapter.py` and declared as an **optional extra**
(`[project.optional-dependencies].bayesian`), NOT a default runtime dependency.
The adapter is the only SRL module that imports `pymc`, `arviz`, or `pytensor`;
every other consumer goes through the typed surface (`ModelSpec`,
`PosteriorResult`, `SummaryStats`, `PosteriorPredictiveCheck`,
`ResourceMeasurement`, `build_model_spec`, `fit_posterior`, `PymcAdapterError`).

### The LGPL `cons` finding (license blocker)

PyMC itself and ArviZ are both Apache-2.0, but **pytensor (PyMC's tensor
backend) unconditionally imports `cons` at import time** — `pytensor/graph/
rewriting/unify.py` does `from cons.core import ConsError, _car, _cdr` during
`import pytensor`, which runs whenever `pymc` is imported. This is a hard
import-time dependency, not a lazy one.

**`cons` is `LGPL-3.0-only`** (declared in its `pyproject.toml`; the LICENSE.txt
is the GNU LGPL v3). The SRL pack policy denies the `LGPL-` prefix outright
(`LICENSE_INCOMPATIBLE_PREFIXES` in `src/srl/packs/manifest.py`), so `cons`
cannot enter the default runtime closure: it would make `license_inventory` fail
and violate the pack license policy. Unlike the `persim`/`hopcroftkarp` GPL
transitive handled for ripser (which is lazily imported and overridable away),
`cons` is imported unconditionally by pytensor, so it **cannot be overridden out
of the closure without breaking `import pymc`**.

### Resolution: optional extra, honest WAIT_LICENSE verdict

Because `cons` is a hard LGPL import of pytensor, pymc+arviz are declared as the
opt-in `bayesian` extra, not default runtime deps:

```toml
[project.optional-dependencies]
bayesian = ["arviz>=0.20,<1", "pymc>=5.20,<6"]
```

This keeps the LGPL package out of the **default** install closure, so
`license_inventory` passes on `uv sync` (the default). The adapter is fully
buildable and testable when the extra is opted into (`uv sync --extra bayesian`);
the `p1-pymc-gate (WP-H71a)` CI job installs the extra, and
`tests/packs/test_pymc_adapter.py` skips itself via `pytest.importorskip` when
the extra is absent (so the default `pytest` run is unaffected).

This is an **honest WAIT_LICENSE-class outcome**, exactly what the P1 admission
framework is designed to produce: the `pymc_arviz` candidate's P1 verdict remains
WAIT_LICENSE (trending REJECT on the LGPL transitive) because `cons` cannot be
cleared against the pack policy. The adapter is **proposal-only evidence**: it
proves the capability is wrappable with a real NUTS sampler and surfaces honest
diagnostics, but it does not move the candidate to `ADMIT_TO_PIPELINE` while the
LGPL transitive is unresolved. Resolving this requires either (a) an upstream
relicense of `cons`, (b) a pytensor build that removes the `cons` import, or
(c) a policy exception for this specific LGPL weak-copyleft case — none of which
this work-package is authorized to grant.

### Version bound rationale

PyMC 6.x and ArviZ 1.x require Python ≥ 3.12, but the project's
`requires-python = ">=3.11"` floor (which also gates the classifiers and the
lock's satisfiability on both 3.11 and 3.12). Bumping `requires-python` is a
cross-cutting policy change beyond this lane's scope. To keep the lock
satisfiable on both supported Pythons without a floor bump, the bounds stay
inside the 3.11-compatible family (pymc 5.x, arviz 0.23.x). The adapter uses
only the stable `pm.sample` / `az.summary` / `az.ess` / `az.rhat` surface common
to both families; no version-specific API is used.

Configuration (see `pyproject.toml`):

```toml
[project.optional-dependencies]
bayesian = [
    "arviz>=0.20",
    "pymc>=5.20",
]
```

### The one-chain bounded profile

The adapter runs exactly one chain (`REQUIRED_CHAINS = 1`) and refuses
multi-chain requests. The rationale (see `docs/architecture/p1-pymc.md`):

1. **CI budget** — a single short chain fits the pack's CI budget with wide
   margin; multi-chain convergence diagnostics across many fixtures would blow
   the budget for a *candidate* pack.
2. **Honest scope** — a single chain cannot compute `r_hat`; the adapter surfaces
   `rhat_max = None` honestly rather than fabricating a value. A one-chain
   posterior is selection-aware evidence, not a convergence certificate.
3. **What one chain still gives** — `ess_min` and the posterior predictive check
   are single-chain-valid, so the adapter reports them as the honest diagnostics
   the profile can read.

The `diagnostics_flag` is `"warn"` when divergences > 0 or `ess_min` falls below
the `ESS_FLOOR` (50); the `rhat_max > 1.01` trigger exists for the future
multi-chain profile but never fires under one chain.

### Size measurement

If PyMC's build were too heavy for the CI 15-minute budget, the ADR would
document a minimal profile. Measured on the resolved closure (CPython 3.12,
arm64), the profile is comfortable:

| package   | installed size | notes                                  |
| --------- | -------------- | -------------------------------------- |
| `pymc`    | ~4.5 MiB       | probabilistic-programming library      |
| `arviz`   | ~4.6 MiB       | exploratory analysis and diagnostics   |
| `pytensor`| ~12 MiB        | transitive; PyMC's tensor backend      |

The full WP-H71a gate (`scripts/checks/wp71a-gate.py`, five checks including two
real NUTS fits) runs in ~10 s, well inside the budget. A minimal profile is not
required.

## Consequences

### Positive

- The first P1 candidate graduates from a typed `WAIT_*` verdict into a built
  adapter, with the missing `actual_compute_adapter` and `resource_measurement`
  evidence supplied.
- A real NUTS sampler is exercised, so the diagnostics surface (`divergences`,
  `ess`) is genuine and the H71a-03 misspecification check is meaningful.
- The restricted declarative spec means no arbitrary code enters the sampler;
  the isolation boundary (this adapter is the only import site) keeps the
  upstream objects out of the SRL type surface.
- The one-chain bound keeps the compute honest and budgeted; the selection-aware
  note travels with every result.

### Negative

- Adds `pymc`, `arviz`, `pytensor`, and their transitive closure
  (`numpy`, `scipy`, `pandas`, `xarray`, `numba`, `llvmlite`, `cons`, ...) to the
  *optional* `bayesian` extra closure (NOT the default runtime closure). All are
  pinned in `uv.lock`. The transitive includes `cons` (LGPL-3.0-only), which is
  why the extra is opt-in; see "The LGPL `cons` finding" above.
- The candidate's P1 verdict stays WAIT_LICENSE-class: the adapter is
  proposal-only evidence, not an admission, because `cons` cannot be cleared.
- The version bound is held below the pymc 6.x / arviz 1.x line to preserve the
  `>=3.11` Python floor. A future floor bump to `>=3.12` (a cross-cutting change)
  would allow lifting the bounds.
- A one-chain posterior cannot certify convergence; consumers must read the
  `selection_note` and the `diagnostics_flag` honestly.

### Security impact

`pymc`, `arviz`, and `pytensor` are imported only inside the adapter and operate
on in-memory NumPy arrays. The adapter performs no network I/O, no shell
execution, and no deserialization of untrusted formats. The model spec is
restricted data (no callable), so a caller cannot inject code. Input arrays are
validated for shape, length, and finiteness before any compute. Pinning the
bounds and recording resolved versions in `uv.lock` bounds the supply-chain
surface.

### Resource impact

Moderate. The NUTS sampler is CPU-bound but the one-chain bounded profile
(draws ≤ 500, tune ≤ 500, chains = 1) keeps a single fit in the low single-digit
seconds for the fixture sizes. The 15-minute CI budget is comfortable; the gate
runs in ~10 s.

### License impact

`pymc` and `arviz` are distributed under the **Apache-2.0** License. PyPI
metadata records `Apache License, Version 2.0` for PyMC and the classifier
`License :: OSI Approved :: Apache Software License` for ArviZ (whose `license`
field is null but whose LICENSE file is Apache-2.0). Both are on the SRL pack
allowlist.

**However, the transitive closure is NOT clean.** pytensor (PyMC's backend)
unconditionally imports `cons`, which is **`LGPL-3.0-only`** — a denied copyleft
license under the SRL pack policy (`LGPL-` prefix). Other transitives in the
optional extra are permissive: `numpy` (BSD-3-Clause), `scipy` (BSD-3-Clause),
`pandas` (BSD-3-Clause), `xarray` (Apache-2.0), `pytensor` (Apache-2.0),
`numba` (BSD-2-Clause), `llvmlite` (BSD-2-Clause AND Apache-2.0 WITH
LLVM-exception), `etuples` (Apache-2.0), `logical-unification`
(BSD-3-Clause). The single blocker is `cons` (LGPL-3.0-only).

Because `cons` is a hard import of pytensor, the `bayesian` extra (and thus
`cons`) is NOT in the default install closure. The CI license inventory
(`scripts/checks/license_inventory.py`) runs against the default closure
(`uv sync`, no extra), where it classifies all installed packages as allowed
with no `denied` or `unknown` entries. When the `bayesian` extra IS installed
(`uv sync --extra bayesian`), `cons` is present and is LGPL-3.0-only; that is
the documented reason the candidate stays WAIT_LICENSE-class.

The pack manifest (`packs/p1-pymc/manifest.json`) declares the license as
`Apache-2.0` for the adapter source and the PyMC/ArviZ distributions; the LGPL
`cons` transitive is documented here and in the candidate's P1 verdict, not
absorbed into the pack license.

## Removal strategy (reversibility)

Reversible. PyMC/ArviZ are isolated behind
`src/srl/packs/adapters/pymc_adapter.py`: that module is the only import site of
`pymc`, `arviz`, or `pytensor` in the SRL tree (asserted by an architecture test
in `tests/packs/test_pymc_adapter.py`). Removing the capability is:

1. a `pyproject.toml` change (drop the `[project.optional-dependencies].bayesian`
   extra);
2. a `uv lock` to drop the transitive closure (including `cons`);
3. deleting `src/srl/packs/adapters/pymc_adapter.py`, the `packs/p1-pymc/` tree,
   the `fixtures/conformance/pymc/` tree, and `scripts/checks/wp71a-gate.py`;
4. the `pymc_arviz` P1 candidate card in `srl.packs.p1` reverts to its honest
   `WAIT_LICENSE` verdict (its `actual_compute_adapter` and
   `resource_measurement` evidence were the only additions this pack supplied;
   the card's removal path is already documented as "pip-uninstall adapter; drop
   capability from registry").

Because the public surface is the only consumer, the gate, the probes, and the
pack manifest would be removed alongside the adapter; no other SRL consumer
imports the typed surface today.

## Evidence

- `pyproject.toml` declares `pymc>=5.20,<6` and `arviz>=0.20,<1` in the optional
  `[project.optional-dependencies].bayesian` extra (NOT `[project].dependencies`),
  so the LGPL `cons` transitive stays out of the default install closure.
- `uv.lock` pins `pymc==5.28.5`, `arviz==0.23.4`, `cons==0.4.7` (LGPL-3.0-only),
  and their transitive closure.
- `src/srl/packs/adapters/pymc_adapter.py` is the sole pymc/arviz/pytensor import
  site; the architecture test `tests/packs/test_pymc_adapter.py` asserts no
  other module imports them. The test skips itself (`pytest.importorskip`) when
  the `bayesian` extra is not installed.
- `scripts/checks/wp71a-gate.py` reports the resolved pymc/arviz/numpy versions
  in its `GateReceipt/v1` evidence block; it runs under the `bayesian` extra.
- The CI license inventory (`scripts/checks/license_inventory.py`) runs against
  the default closure (`uv sync`, no extra) and classifies all installed
  packages as allowed (no `denied` or `unknown`). With the `bayesian` extra
  installed, `cons` (LGPL-3.0-only) would be `denied`; that is the documented
  reason the candidate stays WAIT_LICENSE-class.
- `docs/architecture/p1-pymc.md` documents the one-chain bounded profile, the
  selection-aware interpretation, and what a posterior is NOT (not causality, not
  validation, not convergence certification).
- `packs/p1-pymc/manifest.json` declares `uncertainty` as its capability profile
  and `Apache-2.0` as its license (the adapter source; the LGPL `cons`
  transitive is documented in this ADR, not absorbed into the pack license).
